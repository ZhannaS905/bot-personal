# Личные уведомления FitPP Personal

FitPP Personal добавляет `personalNotificationsV1` в JSON внутри поля
`signature` в квитанции. Поля Firestore-документа остаются прежними.
Транзакция сохраняет снимок события и учётные данные вместе. При повторе
сравниваются исходное действие и день операции. Квитанции прежнего формата
по-прежнему подходят для проверки повтора.

Отдельный процесс читает подтверждённые квитанции `operations` и
`paymentReceipts` в `fitppWorkspaces/personal-v1`. Он выбирает текущего
клиента в существующем реестре `notificationBindings/training-test` по
идентификатору клиента, сверяет бота через `/me` и отправляет личное
сообщение по `user_id` привязки. Числовые идентификаторы старых клиентов
нормализуются так же, как при привязке. В журнал процесса попадают только
коды результата.

Остаток фиксируется в момент операции. Покупка с отметкой «Был» создаёт
два события с остатком после списания. Для разового посещения в сообщении
показывается стоимость. Если к моменту обработки покупку отменили,
отметку заменили или сняли, занятие отменили или клиента архивировали,
событие пропускается. Отсутствующая или выключенная привязка тоже даёт
окончательный пропуск. Квитанции без снимка уведомления пропускаются.

## Конфигурация для отдельного согласования

При включении супервизор запускает воркер отдельным дочерним процессом
рядом с `direct-training-test.cjs`. При ошибке конфигурации или каталога
супервизор пишет `FITPP_PERSONAL_NOTIFICATION_SUPERVISOR_REFUSED` и
пропускает запуск воркера. После выхода воркера повторный запуск идёт
через 5, 10, 20 секунд и далее с пределом в 5 минут. При остановке
супервизора оба процесса получают SIGTERM, затем через 10 секунд
оставшиеся процессы получают SIGKILL.

Используются существующие настройки Personal. Нужны `BOT_MODE=test`,
`FIREBASE_PROJECT_ID=fitpp-personal`, `FITPP_DIRECT_ENABLED=true`,
параметры `FIREBASE_API_KEY`, `FIREBASE_BOT_UID`,
`FIREBASE_BOT_EMAIL`, `FIREBASE_BOT_PASSWORD`, `TEST_EXPECTED_BOT_ID` и
`TEST_BOT_TOKEN` (или `BOT_TOKEN`) того же Bot Personal, который выполняет
привязку. Переменные `AUTO_PUBLISH`, `TEST_ALLOW_SEND`, `TEST_ALLOW_EDIT`,
`TEST_ALLOW_DELETE` должны быть `false`. `OWNER_DIALOG_ENABLED` должен
быть `false` или отсутствовать. `FITPP_NOTIFICATION_SUPERVISED` должен
быть `false` или отсутствовать. Процесс не запускает планировщик
опросов или webhook. Вне текущего образа установить зависимости
`npm ci --prefix direct-sdk` и указать
`NODE_EXTRA_CA_CERTS=/absolute/path/to/russian-trusted-root-ca.pem`.

Новые переменные:

| Переменная | Значение |
| --- | --- |
| `FITPP_PERSONAL_NOTIFICATIONS_ENABLED` | `true` включает запуск воркера супервизором |
| `FITPP_PERSONAL_NOTIFICATION_START_AFTER_REVISION` | Подтверждённая `_fitppRevision` из `states/main` непосредственно перед включением уведомлений. Обрабатываются строго большие ревизии |
| `FITPP_PERSONAL_NOTIFICATION_STATE_DIR` | Абсолютный путь к отдельному каталогу внутри постоянного тома `/data`. Если указан `/data/fitpp-personal-notifications`, супервизор создаёт этот каталог при запуске. Для другого пути каталог должен уже существовать. Каталог должен принадлежать пользователю процесса, иметь права `0700` и быть доступен на чтение, запись и вход |

Супервизор отклоняет символические ссылки и каталоги с неподходящими
правами, сохраняя права существующих файлов и каталогов. Родительские
каталоги от `/data` должны принадлежать root или пользователю процесса
и быть закрыты для записи группе и остальным пользователям. На Linux
супервизор удерживает общий со старым watcher lock, пока управляет
воркером. Если старый watcher уже запущен, воркер пропускается.

Нужен один экземпляр процесса с постоянным томом. Хранить каталог при
перезапуске и восстановлении. На диске находятся курсор и отдельные
метки с хешированными именами. При потере тома снять подтверждённую
текущую ревизию и начать с неё после сверки недоставленных событий.
Повторный старт со старой ревизии и пустым каталогом может дать дубли.

### Firestore

В действующих правилах проверить права существующего отдельного UID
бота. Для уведомлений достаточно следующих прав чтения:

- `get` на `fitppWorkspaces/personal-v1/states/main` и
  `fitppWorkspaces/personal-v1/notificationBindings/training-test`.
  Добавить `allow get: if bot();` к точному пути, если права ещё отсутствуют.
- В каждый существующий `match` для
  `fitppWorkspaces/personal-v1/operations/{id}` и
  `fitppWorkspaces/personal-v1/paymentReceipts/{id}` добавить только:

  ```firestore
  allow list: if bot()
    && request.query.limit <= 25
    && resource.data.type in ['subscription', 'attendance'];
  ```

Здесь `bot()` должен проверять точный `request.auth.uid` текущего
выделенного Firebase Auth пользователя. Бот читает целиком совпавшие
квитанции, включая платёжные поля, поскольку Firestore выдаёт документ
целиком. Уведомления используют снимок события и ID клиента. Проверить
разрешённый запрос и отказ для чужого UID, неограниченного запроса и
других типов в эмуляторе. Для запроса с `type in` и диапазоном по
`revision` подготовить составной индекс с областью `COLLECTION`,
полями `type ASC, revision ASC`, отдельно для каждой из двух коллекций.
Сверить с подсказкой Firestore о недостающем индексе на согласованной
среде. Запись Firestore из процесса доставки не нужна.

### Порядок включения

1. Сверить права, индексы, версию SDK и настройки Bot Personal. Проверить
   запросы в эмуляторе и подготовить постоянный том.
2. Зафиксировать стартовую ревизию. Опубликовать FitPP Personal с новым
   форматом квитанций и включить флаг в контейнере с супервизором. При
   откате UI предпочтительна сборка, сохраняющая разбор
   обоих форматов квитанций для идемпотентных повторов.
3. Провести три подтверждённых операции на согласованном тестовом
   клиенте с привязкой, сверить сообщения и остатки и повторить запуск с
   тем же томом. Для отключения доставки установить
   `FITPP_PERSONAL_NOTIFICATIONS_ENABLED=false` и перезапустить контейнер
   с тем же томом.

Перед запросом MAX сохраняется постоянная метка попытки. Таймаут,
некорректный ответ или остановка процесса после сохранения метки
считаются неопределённым исходом. Автоматического повтора POST нет
и при явном отказе MAX. Это предотвращает дубли ценой возможного
пропуска, в том числе при аварии между сохранением метки и запросом.
Сбой чтения или проверки бота до метки сохраняет событие для следующего
цикла. При недоступной инфраструктуре доставка отстаёт, операции
приложения выполняются независимо.

## Локальные проверки

В `FitPP-Personal` выполнить `node --test tests/*.test.cjs`.
В `bot-personal` выполнить `npm run check`. Новые тесты используют
фиктивные серверные снимки и MAX, а журнал доставки проверяют на
временном диске.
